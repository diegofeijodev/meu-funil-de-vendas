## 0.1 Cross-cutting facts that drive the API surface

1. **Two data paths**: (a) browser talks to Supabase PostgREST directly with the user JWT and relies on **RLS** (workspace membership) for authorization; (b) "server functions" (`createServerFn`, POST, JSON body, Bearer token attached by `attachSupabaseAuth` middleware) for anything involving secrets, AI, Meta/Instagram/Canva/etc. The NestJS API must replace BOTH, i.e. expose REST for every direct table access below with the same workspace-membership/role checks.
2. **Roles**: `owner | admin | marketing | viewer` (`workspace_members.role`). Client flag `canEdit = role !== 'viewer'`; `canManage/canDecide = owner|admin`. While memberships load, `role` defaults to `'viewer'` (so `canEdit` is false until loaded).
3. **Workspace scoping**: nearly every query is `.eq('workspace_id', workspaceId)` where `workspaceId` comes from `WorkspaceProvider` (stored in `localStorage['aimos.workspace']`). Server fns receive `workspaceId` in the body.
4. **Errors**: server fns throw `Error(message)` with pt-BR messages that the UI shows via `toast.error(e.message)`. Some return `{ok:false, error}` instead of throwing (Instagram `connect`, `aiKeysSave`, `aiKeysTest`, `metaAdsTest`, post-editor `run()` wrapper). REST must keep user-facing messages.
5. **Long-running work is orchestrated by the browser**: Instagram auto-calendar `drive()` loop (see 2.11), `generateContentCalendar` (client fakes a progress bar), library per-file upload loops, per-post `generatePostAssets` loop. API must keep these step endpoints idempotent and return the same shapes (`{filled,total,done,busy}`, `{ok,done}`).
6. **Hard-coded external URLs** the API/Next must serve: `/api/public/meta/oauth/callback`, `/api/public/ads/oauth/google|tiktok`, `/api/public/canva/oauth/callback`, `/api/public/mcp/callback`, `/api/public/webhooks/{meta/leadgen|whatsapp|instagram}/{token}`, `/api/public/forms/{token}`, `/api/public/forms/embed/{token}`, `/api/public/unsubscribe/{leadId}`, `/api/public/cron/*`. Canva HowTo text hard-codes `https://www.meufunildevendas.com.br/api/public/canva/oauth/callback`.

### 8.5 Behaviours that need explicit API decisions
1. **RLS replacement**: every direct table read/write in section 2 must be re-implemented behind workspace-membership checks. Per `supabase/migrations`, almost all tables use ONE policy `"ws members full access"` (`for all`, `is_workspace_member(workspace_id)` for both USING and WITH CHECK), i.e. **any member including `viewer` can write at the DB level; the viewer restriction exists only as hidden buttons in the UI**. Decide whether the new API enforces the role matrix (recommended) or mirrors the permissive behaviour.
2. **Client-composed multi-step writes** (non-atomic): Kanban move (3 writes + optional Meta conversion), brand asset upload (storage + insert + logo update), campaign create (insert + strategy + copy + activity), request approval (approval insert + campaign status + activity), lead note (interaction + last_interaction_at), AI toggle (patch + interaction). 3. **`activity_logs` audit** is written from the browser via `logActivity` (and the Approvals page prints `action` + `JSON.stringify(metadata)`): API should log these server-side with the same action strings.
4. **Aggregations done client-side over full tables** (no pagination): `performance_daily`, `crm_leads`, `crm_stage_history`, `crm_interactions`, `creatives`, `campaign_costs`, `ig_posts`, `ig_post_metrics`; library is the only server-paginated list (60/page + count + facets limit 5000).
