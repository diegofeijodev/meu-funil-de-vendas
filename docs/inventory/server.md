# Meu Funil prototype: SERVER-SIDE INVENTORY (for the NestJS + PostgreSQL port)

Source: `/home/doutor/coding/freela/meu-funil/.prototype` (Lovable project, TanStack Start v1.168 + Supabase, `bun`, Nitro build targeting Cloudflare-style edge runtime). Read-only analysis; nothing in the prototype was modified. Language of all user-facing messages is **Portuguese (pt-BR)**: preserve the strings or move them to an i18n catalog.

## 0. Architecture summary (read this first)

- **Two kinds of server entry points**
  1. **117 TanStack `createServerFn` RPCs** (`src/lib/**/*.functions.ts`, 20 files). Each is invoked from the browser as an internal RPC (`POST /_serverFn/<hash>`, JSON or multipart `FormData` for uploads), always with `Authorization: Bearer <supabase access token>` attached by a global client middleware. They are NOT a stable REST surface: the port should expose them as REST endpoints (suggested mapping is the file/function grouping below).
  2. **14 file-based HTTP route files / 19 handlers** under `src/routes/api/public/**` (cron, webhooks, OAuth callbacks, public form, unsubscribe). Unauthenticated at the framework level; each has its own secret/signature scheme (section 2).
- **A large part of data access never touches the server code.** The React app talks directly to Supabase (PostgREST + RLS) with the user's JWT for CRUD on brands, campaigns, creatives, copies, personas, products, crm_leads, crm_tasks, ig_content_plans, etc. (`src/lib/workspace.tsx`, `crm-queries.ts`, `mcp-client.ts`, plus route components). Only privileged or external-API work goes through server functions. For the port, every such table access needs a REST endpoint with workspace/role authorization replacing RLS (see section 7/8). Brand files are also uploaded **directly to storage** from the browser (`creative-assets/brands/{workspaceId}/...`, storage RLS: members read, owner/admin/marketing write/delete).
- **Server-side Supabase access modes:** (a) *user client* (anon key + user JWT, RLS applies) = `context.supabase` from `requireSupabaseAuth`; (b) *admin client* `supabaseAdmin` (service role, bypasses RLS) used for credential vault, cron, webhooks, media library, Instagram pipeline, MCP connections. Many functions mix both. Authorization in admin-client paths is therefore **only** what the function code checks.
- **Global middleware (`src/start.ts`)**: request middleware = error page wrapper (500 HTML) + CSRF protection for serverFn requests; function middleware (client side) = `attachSupabaseAuth` adds the bearer token. `src/server.ts` wraps the SSR handler and replaces h3's swallowed 500s with an HTML error page; `src/lib/error-capture.ts` monkey-patches `console.error` to expand error stacks/causes. `lovable-error-reporting.ts` is Lovable editor telemetry only (drop it).
- **Error convention:** server functions `throw new Error(<pt-BR message>)`; TanStack serializes this to the client as a failed RPC with that message (HTTP 500 for plain errors; auth failures also surface as plain `Error` messages "Unauthorized: ..."). Several functions instead RETURN `{ok:false, error}` (aiKeysSave, instagram publish/connect, generatePostAssets, creative generation). The port should standardize on proper HTTP statuses (401/403/404/409/422/429/502) while keeping the messages.
- **No rate limiting, no request-size limits, no retry middleware** anywhere in the server layer. External API calls have no timeouts (plain `fetch`) except where polling deadlines are coded.
- **Time zone:** all scheduling logic assumes America/Sao_Paulo = fixed UTC-3 (no DST); cron schedules in pg_cron are UTC.

## Totals
- Server functions: **117** (20 files). HTTP route files: **14** (19 method handlers). External providers: **16** (section 3). Env vars/secrets read in code: **29 env names** + 31 fixed vault credential keys (+ 2 per-workspace AI key name patterns) (section 4).

## Auth middleware used by every server function (`src/integrations/supabase/auth-middleware.ts`)
`requireSupabaseAuth` (type `function`): reads `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY`; takes request headers via `getRequest()`; requires `Authorization: Bearer <JWT>` with exactly 3 dot-separated parts; builds a Supabase client carrying that bearer token (RLS applies); validates with `supabase.auth.getClaims(token)` (asymmetric JWT/JWKS verification, no DB call); puts `{supabase, userId = claims.sub, claims}` in `context`. Error messages: "Unauthorized: No authorization header provided" / "Only Bearer tokens are supported" / "No token provided" / "Invalid token" / "No user ID found in token". **The workspace is never derived from the token**: it is always an explicit `workspaceId` (or an entity id resolved to its workspace) in the payload, then checked against `workspace_members` (via `requireRole`/`requireMember`/`assertAdmin`/`assertMember`, each file has its own variant). Role helpers: `membership.ts#requireRole(ctx, workspaceId, roles?)` with `EDITORS=[owner,admin,marketing]`, `MANAGERS=[owner,admin]`; SQL helpers `is_workspace_member(_ws)` and `has_workspace_role(_ws, _roles[])`.

Conventions in the tables below: "member" = any row in `workspace_members` (including `viewer`); "EDITORS"/"MANAGERS" as above; method is always POST for server functions (TanStack `createServerFn({method:"POST"})`).

**Provider resolution (`resolveProvider(supabase, workspaceId, choice)`)**
- `chatgpt` -> `createChatgptProvider(workspace OpenAI key|null)`; `gemini` -> `createGeminiProvider(workspace Gemini key|null)`; null key means "use Lovable AI credits".
- `higgsfield` -> requires live MCP connection else error "Higgsfield não está conectado nesta empresa. Conecte em Integrações."
- `auto` -> chain (`chainProviders`): OpenAI key (strict) -> Gemini key (strict) -> Higgsfield (if connected) -> Lovable credits (`createGeminiProvider(null)`, label "Créditos de IA do app"). The chain advances to the next provider on **any** error (the exported `isCreditError` regex `(402|429|crédito|saldo|quota|cota|limite|esgotad|rate limit|insufficient|billing)` is defined but not used to gate the fallback); log lines like "Usado: ..." / "{label}: {error} → tentando o próximo" are saved in `creative_generation_jobs.provider_log`. Never falls back to a simulated provider. With no own connections only the Lovable credits provider is used.
- Provider costs (internal accounting, USD-ish units): Higgsfield image 1.2/video 4.5 (`CREATIVE_COSTS`); ChatGPT via gateway 1.5; Gemini via gateway image 1.0, Veo via gateway 6.0; own keys cost 0.

### 1.17 Instagram server internals (shared by functions and cron)
**Media generation (`generatePostAssets`)**: loads post (+ plan brand), post -> `generating`; `resolveProvider`; art-director prompt per slide (reuse `creative_brief.visual_prompt_override` for single image); **single image** -> `runImagePipeline` (variations default 3, critic, compose, layouts from `creative_brief.layout/headline/price`); **carousel** -> one image per slide with `composeSlide` (hook on slide 1, CTA on last, logo on all); **reel/story_video** -> video from provider (+ `videoCover` cover with logo/CTA/hook and `.srt`). Async providers: stores `creative_brief.pending_job` and keeps `generating`; cron `pollPendingMedia` finishes (timeout 1 h). End state: `ready` if approval not required else `pending_approval`. Errors: post `failed` + `last_error`.
**Publishing (`publishInstagramPost`)** guardrails (all throw `Guardrail`, non-retryable): post has media; approval obtained when plan/run requires; max 25 published posts per workspace per rolling 24 h (local count + Graph `GET /{ig}/content_publishing_limit?fields=quota_usage`); every `media_assets` row `ig_ready` and not mock/picsum; each media URL answers publicly over HTTPS (HEAD, fallback GET Range 0-0); connected `instagram_accounts` row exists. Then Graph container creation: `POST /{ig}/media` with `image_url` (feed_image), carousel children (`is_carousel_item`, videos `media_type=VIDEO`) then `media_type=CAROUSEL&children=...`, `REELS` (`video_url`, `share_to_feed=true`, optional `cover_url`), `STORIES`; caption = caption + cta + `#hashtags` (<=2200 chars). Saves `ig_creation_id` (resumable), polls container `GET /{id}?fields=status_code,status` until `FINISHED` (budget 40 s; throws `ContainerPending` -> job retried in 2 min without consuming an attempt; ERROR/EXPIRED -> failure), then `POST /{ig}/media_publish {creation_id}` and `GET /{mediaId}?fields=permalink`. Post -> `published` with `ig_media_id`, `ig_permalink`, `published_at`.
**Metrics (`collectPostMetrics`)**: per-format metric sets (reel: views, reach, likes, comments, saved, shares, total_interactions, ig_reels_avg_watch_time; feed_image adds profile_visits; story: views, reach, replies, shares, total_interactions, navigation(breakdown)); on failure retries essential set; inserts `ig_post_metrics` with raw JSON. `collectDueMetrics` runs windows 1h/24h/7d (stories 1h/20h, skipped after 23.5 h) for posts published in last 8 days (limit 200), tracked in `ig_posts.metrics_collected`.
**Account insights (`collectAccountInsights`)**: `GET /{ig}?fields=followers_count,follows_count,media_count,username`; `GET /{ig}/insights?metric=reach,follower_count&period=day&since&until` (30 days); per-day `metric_type=total_value` calls for views, profile_views, website_clicks, accounts_engaged, total_interactions (7 days backfill first time, then 2); upsert `ig_account_insights (workspace_id,date)`.
**Learning (`learnFromTopPosts`)**: from `ig_post_metrics` (60 d) score = reach + 5*saves; top 20% posts per workspace (min 5 posts) copy their `art_direction.prompt_final` into `brands.visual_style.exemplos_prompt` (keeps last 10).

| `ads-insights-3h` | `17 */3 * * *` | `/api/public/cron/ads` `{"task":"sync"}` | `ads-sync` (>4 h) |
| `ads-rules-daily` | `40 12 * * *` | same `{"task":"rules"}` | `ads-rules` |
| `crm-daily` | `10 9 * * *` | `/api/public/cron/crm-daily` `{}` | `crm-daily` (>26 h) |
Note: the Instagram route writes its heartbeat **before** doing the work (`instagram-{task}`), so a fresh heartbeat does not prove success; the ads and cadence routes write it after. Hosting constraint to remember: every cron execution is a single HTTP request (edge/serverless time limits assumed: batch sizes are deliberately tiny: 4 publishing jobs, 2 media generations, 20 pending polls, 200 cadence runs).

## 5.2 Instagram cron task logic (`/api/public/cron/instagram`)
- `queue`: (1) `pollPendingMedia` finishes async media for `ig_posts` with `status=generating` and `creative_brief.pending_job` (provider status poll; max 1 h then failed; continues remaining carousel slides; calls `afterMediaReady`); (2) `pollPendingCreatives` finishes Creative Studio jobs `creative_generation_jobs` with `status=generating` and `external_job_id` (limit 20; fails after 1 h); (3) `runPublishingQueue`.
- **Publishing queue / `publishing_jobs`** (columns: `id, workspace_id, campaign_id?, post_id?, ig_post_id, channel ('meta_ads'|'instagram_organic'), target, status (queued/pending/running/done/failed/partial/cancelled), mode (mock|live), log, run_at, attempts, locked_at, created_at`; index `(channel,status,run_at)`): resets jobs `running` with `locked_at` older than **15 min** to `pending`; selects up to **4** pending jobs `run_at <= now` ordered by `run_at`; **optimistic lock** via `UPDATE ... SET status='running', locked_at, attempts=attempts+1 WHERE id AND status='pending'` returning rows (skip if none); runs `publishInstagramPost`; outcomes: success -> `done` + log permalink + autopilot event; `ContainerPending` -> back to `pending` after 2 min **without** consuming the attempt; `Guardrail` (rule violation) or Meta token error 190 -> no retry, `failed` (token error also calls `handleTokenExpired`: account status error, plans paused, pending jobs cancelled); `RateLimited` -> retry in 1 h without counting; other errors: `MAX_ATTEMPTS=3`, backoff `5 min * 2^(attempt-1)`; post status mirrors (`scheduled`/`failed`, `retry_count`, `last_error`). Jobs are created by `schedulePost` (cancelling previous pending jobs of that post). Meta Ads publish also writes `publishing_jobs` rows (`channel meta_ads`, only as an audit log, never processed by the queue).
- `media`: `revalidateBackfill(20)` (re-validates `media_assets` flagged `quality_report.backfill`), `autoCalendarTick`, `autopilotTick`.
  - `autoCalendarTick`: (1) runs with `ig_auto_runs.status='planning'` get another AI batch (`fillAutoRun`, one run per tick, batch of 8 slots, lock `locked_until`=+150 s); (2) posts with `automation` set and `status in (ready, approved)` are scheduled (`scheduleAutomated`: if late <= 12 h publish in 1 min, if later than 12 h move to same time next day); (2b) failed automatic posts get one automatic retry (`creative_brief.auto_retried`); (2c) `automation=publish` posts overdue <12 h still in `idea` are generated now; (3) `automation=approval` posts not approved 10 min before the slot move to the same time next day; (4) `renewRecurring`: recurring runs keep the next 7 days planned; (5) active runs whose posts are all published/cancelled/failed become `done`.
  - `autopilotTick`: for active plans with `auto_publish` and for posts with `automation`, generates media for up to **2** future `idea` posts (closest first), schedules, and applies the "2 h rule" (unapproved posts of approval-plans due within 2 h are shifted +24 h); logs to `ig_autopilot_events`.
- `metrics`: `collectDueMetrics` (1h/24h/7d windows; stories 1h/20h) then `learnFromTopPosts`.
- `weekly`: `renewRecurring` + for each active auto-publish plan generates next week's calendar (idempotent through `ig_autopilot_weeks (plan_id, week_start)` unique insert; released on failure).
- `optimize`: for active/paused plans with >=3 posts in last 14 d computes best publication hours (BRT) by average reach and pillar weights (70% performance + 30% uniform by keyword match), updates `ig_content_plans.preferred_times`, `pillar_weights`, appends to `ai_notes` (last 20).
- `account`: `collectAllAccountInsights` for every connected `instagram_accounts` row.
- no task: runs queue + media + metrics (compat).
Idempotency/locks summary: job-level optimistic lock + stale-lock reset (publishing); `ig_auto_runs.locked_until`; `ig_autopilot_weeks` unique reservation; webhook ledger; most media functions are not idempotent (duplicates possible if two cron invocations overlap since `pending` ig_posts selection has no lock).

## 5.3 Ads cron (`/api/public/cron/ads`)
`sync` (every 3 h): for each workspace with any Meta/Google/TikTok campaign: last 3 days of Meta ad-level insights -> `performance_daily` upsert (conflict `campaign_id,meta_ad_id,date`) and Google/TikTok daily rows (conflicts `campaign_id,source,external_id,date`). `rules` (daily): additionally `runAllRules` for campaigns with `automation_rules.enabled` (pause expensive / no-lead ads, scale cheap ad sets; see 1.19).

## 5.4 CRM crons
`crm-cadences` (5 min): `applyStageAndTagTriggers` (enrolls up to 200 leads per active stage/tag/campaign cadence, idempotent through existing run lookup); `runDueCadenceSteps(200)`: selects `crm_cadence_runs` with `status=running` and `next_run_at <= now` (ordered), **no locking** (risk of double execution when two invocations overlap); per run: stops if cadence inactive or exit rule hit (opt-out, human takeover `ai_active=false`, stage change, won/lost, reply since entry); outside the step's send window (default Mon-Fri 08:00-20:00 BRT) reschedules at next 15-min slot (max 7 d scan); hourly send budget per workspace (`crm_settings.wa_hourly_limit`, default 30, counted from `crm_messages` out in the last hour) else retry +20 min; executes the step (email via Resend or a call task; WhatsApp text/template with 24 h-window fallback template; Instagram DM for IG-only leads); advances `step_index`, `next_run_at = now + next.delay_minutes`; failures mark the run `failed` with `last_error` (no automatic retry); events in `crm_cadence_events`. `createSlaAlerts(500)` creates `crm_tasks` "SLA estourado em {stage} — {lead}" for leads stuck beyond `crm_stages.sla_hours` (dedupe by title). `crm-daily`: cost import (see route 5).

# 6. Image / video / media pipeline
- **Libraries (all pure JS to run on the edge runtime; no native binaries):** `jimp` v1 custom build (`@jimp/core`, `@jimp/js-jpeg`, plugins blit/color/contain/cover/crop/flip/mask/resize/rotate; PNG codec replaced by `fast-png` in `media/jimp.server.ts` because pngjs needs Node streams); `opentype.js` v2 (parse brand font, glyph outlines -> own polygon rasterizer in `compose.server.ts`; no text rendering by AI); `pdf-lib` (contact sheet / print PDFs, Helvetica standard fonts only); `jszip` (ZIP exports + CapCut package); `unpdf` (PDF text extraction for the SDR knowledge base); `fast-png`. **Not used though documented in AGENTS.md:** `@cf-wasm/photon`. No ffmpeg: videos are never transcoded, only inspected via an MP4/MOV box parser (`media/video-meta.server.ts`).
- **Fonts / assets:** brand-uploaded `.ttf/.otf` (from `brand_assets` kind `font`), default Archivo Black (downloaded from GitHub raw at runtime, cached in memory), brand logo (`brand_assets` kind `logo`, skips svg/pdf), reference photos (`brand_assets` kind `reference`/`photo`, tag `produto|ambiente|equipe`; product-tagged first; sent to the image models as references; shrunk to <=1024 px JPEG q85, 768 px for the critic).
- **Storage buckets (Supabase Storage):** `creative-assets` (private) is the library bucket: `media/{workspaceId}/{YYYY-MM-DD}/{uuid}.{ext}` + `_thumb.jpg`; `{YYYY-MM-DD}/{uuid}.{ext}` for raw provider outputs from `lovable-ai.server`; `exports/{workspaceId}/{uuid}_{name}` for downloads/ZIP/PDF/CapCut; `crm/{workspaceId}/{date}/{uuid}.{ext}` for inbound WhatsApp media; `media/{ws}/{date}/{uuid}-legendas.vtt|srt` captions; `brands/{workspaceId}/...` brand files uploaded by the browser. `ig-media` bucket is declared (`BUCKET = "ig-media"`) and has a service-role read policy but the code does not use it.
- **Signed URLs:** stored permanently in DB columns (`media_assets.url`, `creatives.preview_url`, `ig_posts.media[].url`) as **5-year signed URLs** (`createSignedUrl(path, 60*60*24*365*5)`); CRM media 1 year; export downloads 10 minutes with `download` filename; Instagram/Meta fetch media by these public signed URLs (guardrail HEAD check). Port: use a durable public/CDN or regenerate URLs on read.
- **Image flow (`runImagePipeline`)**: art-director prompt -> N parallel provider generations (1-4, default 3) -> each downloaded and normalized (cover crop to exact size: 1080x1080 feed 1:1, 1080x1350 feed 4:5, 1080x1920 story/reel, 1200x628 ad landscape; JPEG q92 or PNG when alpha) and stored -> vision critic score (0-50) -> best (rebuild prompt once if < 28) -> composition (title band / price pill / CTA button / logo corner, safe zones) -> final asset (`parent_id` = clean winner) -> `creatives` + `creative_versions`.
- **Video flow**: provider generation (Higgsfield `kling2_6` 5/10 s with sound; Veo 3.1/3.0 fast 8 s with audio; image-to-video from brand reference), the request waits <=25 s then the cron resumes; stored as-is (MP4/MOV), validated for Instagram (H.264/AAC, >=720 px width, 9:16 for reels/stories, 3 s-15 min reels, <=60 s stories, 23-60 fps, <=1 GB); captions generated from copy text (6-word chunks over the duration, `.vtt` and `.srt`); optional cover frame = generated still + logo/headline/CTA composition; CapCut zip package.
- **Library actions:** upload (<=500 MB, image/video), reformat to other target formats (images only), PDF/ZIP export (<=250 MB ZIP), download converted PNG/JPG, delete (removes files + rows), tag/folder rename, ad results per creative, attach to Instagram posts or campaigns, revalidate. Uploads of 500 MB through a TanStack server function (FormData in memory) is a scalability smell: use streamed/multipart-to-storage in NestJS.

# 7. Auth model
- **Provider:** Supabase Auth. Email + password (`signUp` with metadata `full_name`, `company_name`; auto `signInWithPassword` right after; if the project requires e-mail confirmation the UI tells the user to confirm). Google sign-in through **Lovable Cloud Auth** (`@lovable.dev/cloud-auth-js`, managed OAuth broker; returned tokens are installed with `supabase.auth.setSession`). No magic link, no password reset or e-mail change UI found in `src`, no MFA, no invitation flow for adding teammates (only the creator exists as `owner`; `workspace_members` rows for others must be inserted by SQL/admin; the `create_workspace(_name)` RPC creates additional workspaces from the browser).
- **Session handling:** supabase-js in the browser, `persistSession`, `autoRefreshToken`, `localStorage` (or Lovable preview iframe postMessage broker `previewAuthStorage.ts` — drop it). Server functions authenticate by bearer JWT per request (section 0). `/auth` page is `ssr:false`; the `_authenticated` layout checks `supabase.auth.getUser()` in `beforeLoad` and redirects to `/auth`. There are no server-side cookies or sessions.
- **Provisioning trigger:** `on_auth_user_created` -> `handle_new_user()` (security definer): inserts `profiles(id,email,full_name)`, a `workspaces` row (name from `company_name` or "Meu Workspace", slug `ws-{10 chars of user id}`, `owner_id`), `workspace_members(role='owner')`, then `seed_demo_workspace(ws)` (demo brand/campaign/performance data marked `source='demo'`).
- **Roles:** enum `workspace_role = owner | admin | marketing | viewer`. Workspace selection is **client-side only** (`localStorage["aimos.workspace"]`, default first membership); the server trusts the `workspaceId` in each request after a membership check. Enforcement points:
  - *Database (RLS):* policy "ws members full access" gives **every member (including viewer)** `FOR ALL` on workspace-scoped tables via `is_workspace_member(workspace_id)`; `workspaces` update only owner/admin; `app_credentials` fully closed; storage policies for `creative-assets/brands/{ws}/` (read: member; write/delete: owner/admin/marketing); triggers (when the JWT role is `authenticated`) `guard_campaign_approval` (only owner/admin may set campaign status approved/active), `guard_approval_decision` (only owner/admin may approve/reject `approval_requests`), `guard_campaign_delivery` (only owner/admin may set `meta_delivery_status` to ACTIVE).
  - *Server functions:* per-function checks as tabulated (owner/admin = connect accounts, save keys, activate campaigns, apply recommendations, create publish-mode calendars; EDITORS = generate/edit; any member = read/diagnostics, and some writes that look like they should be EDITORS: `generateCopyWithAI`, `generatePostAssets`, `schedulePost`, `generateContentCalendar`, `regenerateCaption`, `uploadPostMedia`, `generateCreative` and the CRM send functions are open to `viewer`).
  - *UI:* `canEdit = role !== "viewer"`.
- **Agency model:** a user can belong to many workspaces; `workspaces.ai_inherit_from` lets a workspace reuse another workspace's OpenAI/Gemini keys, Higgsfield MCP connection and Canva connection (single level; set by owner/admin of both).

# 8. Port notes
**Lovable/Supabase-specific pieces that need a replacement design**
1. **Lovable AI Gateway + `LOVABLE_API_KEY`**: used for ALL default text (model id `openai/gpt-6-astra` via the OpenAI **Responses API with streaming SSE and strict `json_schema`**), vision (images as `input_image` data URLs), image generation/editing (`openai/gpt-image-2.5-sunburst`, `google/gemini-3.1-flash-image`), Veo video (`google/veo-3.1-fast` through `/v1/videos`) and SDR model options (`google/gemini-3.1-flash|pro`). Replacement: a provider abstraction in Nest (`TextLlmPort.json(schema)`, `VisionPort`, `ImagePort`, `VideoPort`) with adapters for direct OpenAI/Anthropic/Gemini + a platform-owned key and usage metering/limits per workspace (the prototype's "credits" are Lovable's, shared and invisible). All callers rely on strict JSON schema output + a regex `{...}` fallback parser; keep that contract. Model ids above are Lovable-gateway aliases and must be remapped to real model names.
2. **Supabase Auth + Lovable Cloud Auth**: need own auth (JWT issuance, refresh, Google OIDC, password reset which the prototype lacks, invite flow which the prototype lacks). `auth.users` -> own `users` table + `profiles`; the `handle_new_user` trigger logic (create workspace + owner membership + demo seed) becomes a registration use case.
3. **RLS as the authorization layer**: ~50 tables are accessed straight from the browser. Port must provide REST endpoints + a workspace-scoped guard (decorator `@WorkspaceRole(...)`) and the three `guard_*` trigger rules in domain code; fix "viewer can write via SDK".
4. **Supabase Storage + 5-year signed URLs**: replace with S3/GCS/R2 + CDN; signed URL stored in DB columns is an anti-pattern (store object keys, sign on read, but Instagram/Meta need publicly fetchable URLs at publish time).
5. **pg_cron + pg_net calling the public HTTP endpoints with `x-cron-secret`**: replace with in-process schedulers (`@nestjs/schedule`/BullMQ repeatable jobs); the job logic can be called directly (no HTTP hop, no 120 s limit). Use a real queue with DB-backed locking (`FOR UPDATE SKIP LOCKED`) for `publishing_jobs` and `crm_cadence_runs`; hard-coded domain `meufunildevendas.com.br` appears in migrations, Canva redirect URI and the unsubscribe URL fallback: make configurable.
6. **TanStack `createServerFn` RPC style + client-side orchestration**: some multi-step flows are driven by the browser polling (`fillAutoCalendar` called repeatedly until done; creative generation returns `generating` and relies on cron). Turn these into background jobs + status endpoints.
7. **Edge-runtime workarounds** (pure-JS image libs, `redirect: "manual"` handling in MCP fetch, no sharp/ffmpeg): in Node/Nest you can use `sharp` and `ffmpeg` (real thumbnails, video transcoding/validation) and drop the fast-png/photon hacks; keep opentype-based text composition or switch to `@napi-rs/canvas`/sharp SVG compositing.
8. **`AsyncLocalStorage` workspace context for Meta calls (`runWithMetaWorkspace`)**: fine in Nest (use `nestjs-cls`) but prefer passing workspaceId explicitly.
9. **Lovable editor artifacts to delete**: `lovable-error-reporting.ts`, `previewAuthStorage.ts`, `integrations/lovable/index.ts`, `@lovable.dev/vite-tanstack-config`, AGENTS.md block.

**Secrets encryption scheme (`credentials.server.ts`)**: AES-256-GCM through WebCrypto; key = `SHA-256(CREDENTIALS_ENCRYPTION_KEY)` (single hash, no salt/KDF), random 12-byte IV per value, stored text `enc:v1:{base64 iv}:{base64 ciphertext+tag}`; no AAD (ciphertext is not bound to workspace/key name), no key id/rotation; **if the env var is missing the value is written in plaintext** and legacy plaintext values are still read; if decryption fails (changed key) the credential silently reads as null (`console.error` only). Not encrypted at all: `mcp_connections` tokens/secrets, `cron_tokens`, webhook/verify tokens. Port: envelope encryption with KMS (per-record data key or master key id), AAD = workspaceId+key, key versioning, fail closed when no key, migrate MCP tokens into the vault, never return secrets (functions only return hints like `••••last4`).

**Bugs / risks worth fixing during the port**
- IDOR / tenant isolation: CRM send/enroll/stop functions and `saveCadence` use admin client with entity ids not scoped to the checked workspace (1.21/1.22). `mcpRun` args are arbitrary. `previewAutoCalendar` has no role check.
- Role gaps: `metaAdsSaveCredentials` allows marketing role (other connect actions require owner/admin); viewer can call many mutating functions; direct SDK writes allowed for viewers by RLS.
- CRM server functions have **no input validation** (identity validators), unlike all other files that use zod.
- Z-API/Evolution webhooks authenticated only by an unguessable path token (no HMAC); MCP and Google/TikTok OAuth states are not bound to the initiating user/session; Meta OAuth `u` field unused.
- Unsubscribe token: truncated HMAC, non-constant-time compare, hard-coded fallback secret `"meu-funil-unsubscribe"`, never expires, and the secret is shared with cron tokens (rotating `CRM_CRON_SECRET` invalidates links).
- Concurrency: `runDueCadenceSteps` has no locking; `pollPendingMedia`/`autopilotTick` select-then-generate without lock; `fillAutoRun` uses an optimistic lock (good).
- Multiple Graph versions: Marketing/IG `v24.0` vs WhatsApp/media `v21.0`; Google Ads default `v21`.
- Credentials for Google Ads/TikTok/Canva/Meta can be set globally (`workspace_id NULL`) and silently fall back to env: define whether the port is single-tenant-per-platform or per-workspace apps.
- Provider "mock/sandbox" paths still exist in code (`isMockMedia`, `mode mock`, `sandbox`): removed in the port; publishing is hard-blocked for mock media.
- Instagram `publishInstagramPost` API returns `{ok:false}` rather than HTTP errors; `schedulePost` returns `sandbox:true` when no account (legacy).
- `media/export.functions.ts#uploadMedia` accepts 500 MB in memory; `capcutPackage`/`exportZip` build zips in memory (250 MB cap): stream in the port.
- Data model hints for the DB team: workspace-scoped tables seen in server code (`workspaces`, `workspace_members`, `profiles`, `brands`, `brand_assets`, `brand_learnings`, `personas`, `products`, `campaigns`, `campaign_strategies`, `copies`, `creatives`, `creative_versions`, `creative_generation_jobs`, `media_assets`, `approval_requests`, `activity_logs`, `ai_recommendations`, `performance_daily`, `publishing_jobs`, `instagram_accounts`, `ig_content_plans`, `ig_posts`, `ig_post_metrics`, `ig_account_insights`, `ig_auto_runs`, `ig_autopilot_events`, `ig_autopilot_weeks`, `mcp_connections`, `app_credentials`, `cron_tokens`, `cron_heartbeats`, `crm_*` (pipelines, stages, leads, interactions, tasks, messages, conversations, integrations, webhook_events, cadences, cadence_runs, cadence_events, sdr_agents, sdr_documents, sdr_runs, settings, wa_templates, campaign_costs, stage_history, tags, loss_reasons, quick_replies)).
